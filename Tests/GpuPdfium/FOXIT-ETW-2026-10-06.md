# Foxit elevated CPU capture, 2026-10-06

## Method and scope

User authorized elevated profiling, with no interference with other screens.
Capture-FoxitStacks.ps1 launched hidden and recorded WPR CPU for 60 seconds.
No window activation, mouse, keyboard, debugger attachment or process dump was
performed. User was invited to zoom/pan manually; exact actions and phase
markers were not recorded. This is an observational capture, not a controlled
latency comparison on a confirmed page/zoom sequence.

Process: FoxitPhantomPDF.exe, PID 45364, installed under Program Files (x86).
ETL: Tests/bin/foxit-study/foxit-cpu-20261006-141934.etl (ignored output).
Trace spans 82.946 seconds including stop/rundown. Lost events/buffers: zero.
Capture completed and the owned recording stopped.

## What this changes

- No substantial CPU parallelism inside this Foxit process was observed.
  This contradicts treating a many-worker renderer as an established Foxit fact.
- This capture does not support a claim that heavy PDF rendering was primarily
  D3D11 GPU work. Sparse D3D samples do not prove absence of every GPU path.
- The EXE and ntdll dominate, but module-level samples cannot distinguish PDF
  traversal, rasterization, allocation, copying or unrelated UI code.
- There is no basis here to assert whole-page versus tiled rendering, bitmap
  versus display-list caching, or exact invalidation/cancellation policy.

Windows public-symbol resolution was attempted but did not finish in the
bounded analysis window; the analyzer was interrupted, not Foxit. Private Foxit
function names remain unavailable. No internal algorithms were reconstructed.

## Next controlled experiment

Repeat with confirmed document/page and timestamped phases: idle, first zoom,
revisited zoom, rapid alternating zoom and pan. Correlate CPU stacks with frame
presentation and application request telemetry. Resolve system frames to
separate allocation/copy/wait from engine work; map dominant private offsets
only when supported by API-call evidence. This can narrow mechanisms without
pretending an ETW CPU capture exposes cache contents.

For our app keep the measured balanced single-viewport-crop default. The
two-worker option trades lower batch latency for duplicated native page memory;
it is not proven to reproduce Foxit's behavior. Prioritize obsolete-request
latency, bounded caches and input/presentation responsiveness before a new engine.

## Reproduction

Use xperf -a dumper with provider ce1dbfb4-137e-4da6-87b0-3f59aa102cbc on the
saved ETL, then run Summarize-FoxitSamples.py <csv-path> --pid 45364.
Raw ETL/CSV remain ignored and may contain other-process metadata; only the
Foxit aggregate is documented here.
