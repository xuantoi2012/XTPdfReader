# GPU PoC Results - 2026-10-05

## Decision

The GPU path is feasible on this RTX 4070, but the useful architecture is
**record once, replay selectively, reuse rendered textures while interacting**.
Moving the existing direct-render call to GPU alone is not a reliable speedup.
Keep the production renderer unchanged until a tiled native-viewer prototype
passes presentation latency, memory and full fidelity tests.

For the next prototype, use one shared GPU context, a provisional 64 MiB Skia
resource-cache budget, bounded per-page pictures and tiles for the active tab.
Inactive tabs must not each retain an independent GPU context/cache. Use cached
textures during gestures, refine exposed/zoomed tiles asynchronously and preserve
the existing CPU fallback. 64 MiB is a measured starting point, not a global
optimum or a total-RAM guarantee.

## Rendering

Hardware renderer confirmed: ANGLE, NVIDIA GeForce RTX 4070, Direct3D11.
Same pinned PDFium/Skia core on CPU and GPU. Two large PDFs (~173 / ~162 MiB),
two pages each, three fresh processes per page, 30 measured transforms per mode.
Below-normal process priority, offscreen, no desktop control. Original inputs
passed before/after SHA256 checks. Three warmups; completion-synchronized GPU.

Values below are averages of the three per-run medians, in milliseconds.

| PDF / Page | Direct CPU | Recorded CPU | Recorded GPU | Direct GPU | Cached Texture GPU |
|---|---:|---:|---:|---:|---:|
| 2.1 / 11 | 10.88 | 7.19 | 0.79 | 4.00 | 0.045 |
| 2.1 / 30 | 63.43 | 24.54 | 22.10 | 75.51 | 0.143 |
| 2.2 / 11 | 62.47 | 13.26 | 7.94 | 51.36 | 0.197 |
| 2.2 / 30 | 24.47 | 5.69 | 4.11 | 21.69 | 0.046 |

The direct-GPU case on 2.1/page30 is slower than direct CPU. This separates
PDFium traversal/CPU setup costs from rasterization; caching the display list
matters substantially. GPU benefit over recorded CPU is much smaller on that
page than the benefit over direct CPU. It contains ~81,384 recorded operations;
2.2/page11 has ~243,294. Operation count alone does not predict rendering time.

Worst recorded-GPU p95 among the three 30-frame runs was 32.02 ms on 2.1/page30.
Thus a fresh full-quality render at every input event cannot guarantee 60 FPS.
Cached-texture timing does not include presenting a frame or producing missing
tiles: **do not convert these timings to advertised viewer FPS**.

Recording averaged 30-62 ms after page load in these runs. First GPU replay
averaged 64-159 ms, plus GPU/context setup (~140 ms in follow-up runs).
Opening/parsing remains CPU work; initial rendering is not magically instant.

## Memory / Cache Tradeoff

GPU-only process, 2.1/page30, 60 frames repeating the same 30-transform cycle,
three fresh processes per budget. Private bytes taken after replay, before
quality readback/reference rendering. They include PDF data, driver and CPU-side
geometry. Not directly comparable to the production WPF application's RAM.

| Skia Cache Budget | Mean Per-Run GPU Median | Private Bytes After Replay |
|---|---:|---:|
| 32 MiB | 61.92 ms | 392.7-394.3 MiB |
| 64 MiB | 19.25 ms | 437.0-439.1 MiB |
| 128 MiB | 17.31 ms | 495.6-499.1 MiB |

64 MiB saves approximately 60 MiB process private memory versus 128 MiB for a
roughly 2 ms replay cost in this cycle. 32 MiB causes substantial cache churn.
An earlier continuously increasing zoom sweep showed different totals and
negligible 64/128 speed difference; workload and cache reuse matter.

Same-cycle stress with 64 MiB: 60 frames ended at 441.7 MiB after replay;
300 frames ended at 439.8 MiB. No sustained growth appeared in that bounded
cycle. A different sweep through 300 distinct zoom levels reached 675.3 MiB;
new geometry/driver allocations still require explicit lifecycle testing.
Freeing Skia GPU resources and destroying the Skia context did not immediately
return most process private bytes to Windows. This does not establish a leak,
but it means cache purge alone is insufficient evidence of RAM control.

Reported Skia GPU-cache usage was approximately the configured budget in the
complex cases. Total dedicated/shared VRAM was **not independently measured**.
Resource budgets must be complemented by process/VRAM telemetry before release.

## Quality And Remaining Gates

All four page samples were nonblank. Recorded CPU replay matched direct CPU
pixels exactly at the checked transform. GPU RGB mean absolute errors were
0.026-0.579 on a 0-255 scale. On the visually inspected CAD samples, text,
linework and dashed lines remained visible, with edge-antialiasing differences.
This is not a complete fidelity certification, particularly for fine lines,
transparency, raster fallbacks, annotations, forms or optional-content layers.

Next useful test is a native tiled viewer surface with real presentation/input
latency measurements. Avoid GPU-to-CPU bitmap readback per frame; otherwise
copies can erase the measured GPU advantage. Compare it to the current app,
not just this Skia CPU benchmark, and stress multiple tabs plus resource release.
No migration of the entire WPF application to C++ is justified by this PoC.
