## 1. Duplicate and Bring to front (done)
- Two icon buttons at the end of the shape bar and the text bar (`ReaderWindow.PropertyActions.cs`). **Duplicate** copies the selection 12 pt down-right (the other way near the right / bottom edge); a group (shape + text boxes) is copied as a new group; the copy is selected; one undo step. **Bring to front** rewrites the selection (a group in its own order) so it ends last in `/Annots`.
- `AnnotationStore.Compute` put a rewritten annotation back at its old index, so on screen the stacking only changed after Save. A spec rewritten from scratch (`ObjectNumber == 0`) now goes to the end at once, exactly where Save puts it; a file annotation that is only moved keeps its place.
- Tests: `TestPropertyActions`, `TestPropertyActionsOnGroup` (`Tests/PropertyBarTests.cs`, which also holds the `RunReaderFlow` helper for the next steps); rendered check `results/property-actions-duplicate.png`.

## 2. Dash style for shapes (done)
- `ShapeStyle` has a fifth field `Dash` (Solid / Dashed / Dotted). It is written only when not solid, so old files and solid shapes keep their exact text and decode as solid.
- Appearance stream (`PdfQuickAnnotationService.AddShape`): `/BS /S /D /D [..]` plus `SetLineDash` (dashed = 4w on / 2.5w off with butt caps; dotted = round dots every 2w). The on-screen layer draws the same appearance, so file and screen match. The arrow head stays solid.
- Live preview (`ShowShapePreview` -> `ApplyDash`) uses the same factors. Property bar: "Line style" combo after the width; the choice is remembered per tool with colour and width, and a selected shape's style is shown in it.
- Test `TestShapeDashStyle` (`Tests/PropertyBarTests.cs`): encode / decode compatibility, bar changes the selected shape, /BS written into a copy the way Save does; rendered check `results/shape-dash.png`.

## 3. Opacity for shapes and text (done)
- `ShapeStyle.Opacity` and `TextFormat.Opacity` (percent, 100 / 75 / 50 / 25). Written only when below 100 (shape: after the dash field, so a shape with opacity always carries its dash), so old files and opaque annotations keep their exact text.
- File: the annotation gets `/CA` and the appearance stream sets an ExtGState with the same fill / stroke alpha (shapes in `AddShape`, text boxes in `AddTypewriter`). Because the on-screen layer shows the same appearance, screen and file match. The shape preview and the in-place text editor fade too.
- Property bar: "Opacity" combo after the line style (shapes) and after the colours (text). Callout text has no opacity (the combo is hidden for callouts); the text-box default remembers the last opacity like the other text settings.
- Test `TestOpacity` (`Tests/PropertyBarTests.cs`); rendered check `results/opacity.png` (25 % and 50 % lines, 75 % text).

## 4. Fill colour for closed shapes (done)
- `ShapeStyle.Fill` (hex, "" = none) for rectangle, cloud and oval; a seventh field, written only when set (then the dash and opacity fields come before it). A line or arrow never keeps a fill. Palette in `ShapeStyle.Fills`: none, white, yellow, red, green, blue, purple, grey (soft tints, so the drawing underneath stays readable; the opacity combo makes them see-through).
- File: the annotation gets `/IC` and the appearance stream fills then strokes. The cloud's bumps are separate half-discs, so the inner rectangle is added to the fill pass and the outline is drawn after it. The shape preview shows the fill too.
- Hit test: the inside of a filled shape is now clickable (an open one still only reacts on its outline). Property bar: "Fill colour" combo after the line style, hidden for arrows and lines.
- A shape whose opacity is not one of 100 / 75 / 50 / 25 (e.g. written by another program) shows 100 % in the bar until changed.
- Test `TestShapeFill` (`Tests/PropertyBarTests.cs`); rendered check `results/shape-fill.png`.

## 5. XT Capture: screen capture as its own always-running program (first version, built)
Owner decisions (2026-10-08): capture is not part of the Reader window. **XT Capture** (`XTCapture/`, `XTCapture.exe`) is a separate small program, built and installed with the Reader, that lives in the tray; it starts with Windows (a setting, on at first run); shortcut Win+C; a half see-through capture button in the bottom right corner of the screen. One capture tool: the Reader's SnapShot tool was removed (it did the same job on the PDF page only); the Reader's Capture and Store buttons start XT Capture. Every capture is kept in XT Capture's **Store**; comments drawn on a capture must stay editable later, and the store is not PDF (PDF is an export option).

- **Projects**: `XTCapture.Core` (overlay, screen grab, region maths, handles, Store, shortcut, settings; no PDF code) and `XTCapture` (WinExe: tray, corner button, Store / preview / settings windows, toast, autostart, command pipe, PDF export with iText loaded only on export). `Services/CaptureLauncher.cs` in the Reader starts it (`XTCapture.exe --capture | --store | --settings | --exit | --background`); a copy that is already running takes the command through the pipe `XTCapture_Command_<user>` and the new start exits. `AppUpdateService` asks it to quit before an update replaces the files. `Build-Release.ps1` publishes both into the same folder: one Velopack package.
- **Overlay** (`CaptureOverlayWindow`): frozen, dimmed screen of all monitors; a white crosshair (with a dark under-line so it shows on light windows) replaces the black cursor; mode bar with icon and text (Window, Rectangle, Circle, Polygon; keys W R E P). Window mode: dashed frame with title and size, Tab or the wheel cycles the windows behind, a covered window is asked to paint itself (`PrintWindow`) and falls back to the frozen pixels. Rectangle / Circle: drag or two clicks. Polygon: click corners, close by clicking the first one, double-click or Enter, Backspace removes the last. **Handles** after a pick (all kinds, also a picked window): eight on a rectangle / circle, one per corner on a polygon, drag inside to move, a click outside starts over; the pointer shows resize arrows. Bar: Copy (Enter), Store, "Outside: white / clear" (circle, polygon).
- **Corner button** (`FloatingCaptureButton`): 48 px, 50 % opaque until the pointer is over it, always on top, never takes focus, not in Alt+Tab; click = capture, drag = move (remembered; falls back to the corner when its place is no longer on a screen), right-click menu (Capture, Store, Settings, Hide this button, Exit). It and the Store are hidden while the screen is frozen.
- **Shortcut** (`HotkeyService`: `RegisterHotKey` on a message-only window, no keyboard hook): Win+C is already taken by Windows (Copilot) on the owner's PC (registration fails with error 1409; Win+Shift+C and Ctrl+Alt+A are taken too). - **Store** (`CaptureStore`, `%LOCALAPPDATA%\XTCapture\Store\<capture>\`: `original.png` as taken, `thumb.png` 360 px, `meta.json`; `markup.json` is reserved for the comments of the next step). Copy puts a bitmap and a PNG (which keeps the clear area) on the clipboard.
- **Settings** (HKCU\Software\XTCapture; the theme and accent are read from the Reader's key so both programs look alike): start with Windows (HKCU Run value with `--background`), corner button on / off, shortcut, clear or white outside the shape.
- **Tests** (`Tests/CaptureTests.cs`, in `--ui-smoke`, 125 checks): region maths and cut-out, handles, Store, shortcut parsing / registration / fallback / message, settings, autostart (a test value name), command pipe and the Reader's launcher, the real screen grab, the overlay driven like a mouse (hover, Tab, covered window, handles, drag, two clicks, circle, polygon), corner button, the tray flow (Copy and Store keep the picture and open the Store). ## 6. XT Capture: drawing and comments (built)
Drawn objects are kept beside the untouched picture and stay editable. The same drawing code serves the frozen screen and the capture editor.

- **Objects** (`MarkupModel`, `markup.json` = `{"v":1,"items":[...]}`, all in pixels of the picture): rectangle, circle / ellipse, arrow, line, pen stroke, text (multi-line), numbered marker, mosaic. Style = the Reader's choices as data: colour (8), width, solid / dashed / dotted, opacity (100 / 75 / 50 / 25), fill (rectangle, circle), font, size, B / I / U; for a mosaic the width is the block size (8 - 32 px). A damaged `markup.json` reads as "nothing drawn" and never blocks the picture.
- **Logic without a screen** (`MarkupController`): tools, objects, selection, move, resize, text start / commit, numbering (next free number, drag right after placing), style applied to the selected object or the next one, undo / redo (200 steps, a drag is one step), delete, bring to front, nudge, clamp to the picture. `MarkupGeometry` (picking: outline, filled inside, text box, marker disc, nearest pen segment; topmost wins; handles: eight on boxes, two on lines and arrows) and `MarkupRenderer` (one draw routine for screen and file; `Flatten`, `Pixelate`).
- **At capture time**: after an area is picked, the bar beside it has three rows: the tools (Select, Rect, Circle, Arrow, Line, Pen, Text, Number, Mosaic with icon and text, undo, redo, delete), the properties of the tool or the selected object (colour, width, dash, opacity, fill / font / block), and Copy / Store. A drawing tool draws inside the area (a click outside does nothing); Select moves and resizes the drawn objects first, then the area's own handles; Esc leaves the tool first; Delete, Ctrl+Z, Ctrl+Y. Drawing is clipped to the area, kept in absolute screen pixels while the area is adjusted, and travels with the capture relative to the area; a click outside the area is ignored once something is drawn (only Esc starts over). Copy puts the flattened picture on the clipboard; the Store keeps the picture as taken + `markup.json`, and the list picture shows the drawing.
- **Editing later** (`EditorWindow`, from the Store card: click the picture or "Edit"): the picture fitted to the window (Ctrl + wheel zooms, Fit), the same toolbars, Save (Ctrl+S; the title shows "not saved"), Copy, PDF; closing asks to save. One editor per capture. Text objects reopen in their typing box (double-click, or a click with the Text tool).
- **Export to PDF** (`PdfExporter`): one page (1 px = 0.75 pt). Choice when something is drawn: everything baked into the picture, or **real PDF annotations** for rectangles, circles, lines, arrows (closed head), pen strokes (Ink) and Latin texts (FreeText, Helvetica), with colour, width, dash, opacity and fill; numbered markers, mosaics and texts with letters the PDF base font lacks (Vietnamese) are baked into the picture. The annotations carry no appearance streams of their own: the Reader's MuPDF engine drew them correctly (`results/capture-pdf-annotated.png`; the arrow head is an open head there), but other viewers were not tried.
- **Tests** (`Tests/MarkupTests.cs`, in `--ui-smoke`, 122 checks; the whole smoke run is 429): JSON round trip, picking and handles, the controller (all tools, text, markers, move / resize, style, undo, clamp), flattening pixel by pixel (outline, fill + opacity, dash gaps, mosaic blocks, text, marker number, arrow head, pen), the toolbar (properties per kind), the overlay with drawing (clip, outside click, Esc, Delete, relative coordinates), the Store with markup, the editor (draw, type, save, reopen, edit text, undo back to clean), PDF export (annotation kinds, dash / fill kept, rendered by the Reader's engine). Rendered checks: `results/markup-sample.png`, `capture-overlay-markup.png`, `capture-editor.png`, `capture-pdf-annotated.png`.
- **Not done / not checked**: the typing box and combo drop-downs on the real frozen screen with a real mouse (the Reader had pointer bugs of this kind), keyboard shortcuts for the tools, highlighter pen, rotating or resizing text by dragging (size comes from the bar), a marker's number cannot be edited, no copy / paste of objects.


## 7. OCR of scanned pages (built)
Owner: "Windows OCR and commercial SDKs excluded; Vietnamese engine choice open" -> decided here: **Tesseract inside PyMuPDF** (already shipped, Apache-2.0) with the `vie` data of tessdata_fast (0.5 MB, Vietnamese + Latin letters and digits). No new program, no new native files: `OcrWorker.py` + `tessdata/vie.traineddata` are added to the package.

- **Choice measured** on synthetic Vietnamese sheets (Arial text at 300 dpi, crisp and a softened, grainy "scan"): fast data and the large `best` data read about the same (word recall 0.91 vs 0.92 crisp, 0.92 vs 0.86 soft), `best` is 3x slower and 25x bigger, so `fast` it is. RapidOCR / PaddleOCR (onnx) would add about 90 MB of wheels; EasyOCR is far heavier. Real drawings may read worse than these tests; the owner's own scans are still the real test.
- **A MuPDF quirk handled**: its OCR text keeps the gap in front of a word but often writes no space character there with Vietnamese letters ("Tylệ", "Sốhiệu"). `OcrWorker.py` splits words at those gaps (recall 0.65 -> 0.92). Also `pix.pdfocr_tobytes` writes text that extraction does not return, so each tile is put on a scratch page and read with `get_textpage_ocr`.
- **Pipeline**: `OcrService` runs `OcrWorker.py` in its own python process (below-normal priority, in the worker job so it dies with the app, cancellable) and reads one JSON line per page: words as fractions of the DISPLAYED page, so any /Rotate works. Big sheets are read in 3200 px tiles with a 160 px overlap, each word kept by the tile that holds its centre, blank tiles skipped. Pages that already have text are skipped by default. `PdfOcrWriter` writes a COPY ("name (OCR).pdf", numbered if it exists) with an invisible text layer (render mode 3): each word on its own box, stretched to its width, turned with the page rotation, in an embedded Arial subset (Vietnamese letters; Segoe UI / Tahoma fallbacks; Helvetica without accents if none is installed). The original is never changed.
- **In the Reader**: ribbon Document > **OCR** (also Ctrl+K), and Find's hint "N pages have no searchable text" now has a "Read the scanned pages (OCR)..." link. The dialog (`OcrWindow`): this page / all pages / a list like 1-3, 7; skip pages that already have text; progress and Cancel; at the end the copy opens in a new tab. It warns when the file has unsaved changes (OCR reads the saved file) and asks for the Modify permission.
- **Sheet numbers from scans**: the sheet-info / title-block reader only needed a text layer; on the OCR copy it reads a region (test: the sheet number region reads "KC-02" on pages rotated 0 / 90 / 270). `TitleBlockReader.MapPoint` was split out of `ToUserSpace` for the writer.
- **Tests** (`Tests/OcrTests.cs`, in `--ui-smoke`, 40 checks): the words (recall 0.94 crisp, 0.96 soft; 5 pages in about 1 s), skipped pages, progress, positions, the copy (size, rotations kept), the viewer finds 35+ words per page and 95 % of them lie on the drawn lines on pages rotated 0 / 90 / 270, Find finds "thiet ke" on the scanned pages (nothing before), the sheet-number region, the skip option, cancelling; the dialog (page lists, defaults, a bad list, pages 2-3 only, a page with text).
- **Not done / limits**: pages scanned sideways or upside down (no orientation detection; a page whose picture is turned but whose /Rotate shows it upright is fine); handwriting; very faint scans (no clean-up step: deskew, contrast); capitals with stacked marks are the weakest ("KET" for "KET"); only Vietnamese + Latin (other languages need their `.traineddata`); the OCR runs on the saved file; no "replace the original" option (a copy keeps it safe).
- **Licences**: `docs/THIRD-PARTY-LICENSES.md` is the AGPL review the pending list asked for: MuPDF / PyMuPDF and iText are AGPL-3.0 (or commercial), what that means for giving the program to people outside the company, and four options (keep internal, open source under AGPL, buy licences, replace the parts). **Decision for the owner.**
