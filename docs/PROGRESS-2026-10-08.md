## What was built
1. **Size and code protection of the Python part**
   - `Packaging/Prepare-MuPdfRuntime.ps1`: prunes the embedded Python (99 MB to ~59 MB) and ships bytecode only (stdlib + PyMuPDF), ~145 ms to import pymupdf. Checked with OCR.
   - `Packaging/Release/Protect-Scripts.ps1`: worker `.py` files compiled to bytecode under the same names.
   - TFM `net10.0-windows` (was `...-windows10.0.19041.0`) for Reader, XTCapture, XTCapture.Core: drops `Microsoft.Windows.SDK.NET.dll` (23.7 MB). No WinRT is used anywhere. Publish went 306 MB (self-contained) to 74 MB (framework-dependent).
2. **License client** (`Licensing/`, `Controls/LicenseWindow.cs`, server in `Licensing/Server/`): signed ECDSA tokens, DPAPI store, 7-day offline grace, clock-rollback check, start-up gate. OFF while `LicenseConfig.SupabaseUrl/AnonKey` are empty; `Build-Release.ps1` refuses to pack without them unless `-AllowUnlicensed`. 20 checks: `XTPdfMergeApp.PerformanceTests.exe --license-check`.
3. **Installer** (`Setup/`): one exe = installer + appended zip (`Setup/Payload.cs`). Real work staged in `<install>.staging`, swapped in at 83 % (`Installer.CommitFraction`); the X button asks (custom dialog) and a cancel before that leaves the machine untouched. Asks to close the running app (waits 8 s when started by an update). Writes Uninstall.exe, HKLM uninstall entry, shortcuts (all users), and the Default-apps registration for `.pdf` (`PDFReaderPro.Document`, Capabilities, RegisteredApplications). `--silent`, `--launch`, `--uninstall`, `--seconds N`, `--sandbox DIR` (test run, HKCU, no UAC with `__COMPAT_LAYER=RunAsInvoker`).
4. **Start-up splash** (`Controls/StartupSplash.*`, `App.xaml.cs`): shown right after the single-instance check, also for a double-clicked PDF; closes when the session is up and the first page is on screen; steps aside for any other window (restore prompt, password, sign-in); 20 s safety limit.
5. **Default PDF app**: Settings > Integration > "Open PDF files with this app" (`Services/DefaultPdfAppService.cs`). Windows protects the default choice, so the button registers the app (HKCU if the setup did not) and opens Windows Settings > Default apps.
6. **Updates** (`Services/AppUpdateService.cs`, `Controls/UpdateReadyWindow.*`, `ReaderWindow.Update.cs`): check 5 s after start; a title-bar "Cập nhật" button appears only when a newer release exists; the offer window shows the notes; "Cập nhật ngay" downloads (progress bar) and starts the setup with UAC, the app exits and the setup reopens it; "Để sau" downloads nothing and the next start offers it again. Dev test hooks: `XTPDF_UPDATE_FEED` (URL of a local feed; asset may be `http://127.0.0.1`), `XTPDF_UPDATE_SETUPARGS`.
7. **Look**: brighter ambient background (`Controls/AmbientBackdrop.xaml`) shared by splash, installer, dialogs and the update window; button hover/focus restyled (white veil, thin light ring).
8. **Release tool**: `Packaging/Release/Build-Release.ps1 -Version x.y.z [-AllowUnlicensed]` builds `Packaging/Release/_release/PDFReaderPro-Setup.exe`. XTAdmin has a "Phát hành PDF Reader" page that runs it and publishes to `PDFReaderPro-Releases` (see the XTAdmin repo).

## Known gaps and next steps
- Setup is unsigned and the downloaded update is not hash-checked (the release body carries a SHA-256; the app does not compare it yet). Signing after the payload is appended would break the file: sign the installer stub first.
- No forced/minimum version, no release-notes channel beyond the GitHub body, only a start-up check (no periodic check in a long session).
- Native C++ MuPDF worker (removes Python: about -30 MB, ~100 ms faster worker start, no `.py`): `Tests/MuPdfNativeWorker` only does page one; text edit and OCR not ported. Postponed.
- .NET assemblies are not obfuscated; planned as the last release step with a commercial tool.
- A shared installer engine for XTToolbox (acad.exe check, AutoCAD version choice) is possible later by moving `SetupWindow`, `ConfirmDialog`, `Styles.xaml`, `Payload`, staging/cancel and the running-process check into a library; deliberately not done now.
- Dev scripts under `Tests/` still point at `bin/Release/net10.0-windows10.0.19041.0`; the output folder is now `net10.0-windows`.
